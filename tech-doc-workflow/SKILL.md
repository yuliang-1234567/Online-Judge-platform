# 三层记录工作流

目标：让读的人在对的地方找到对的信息。代码注释解释一段代码为什么这样写；模块文档解释一个模块由什么组成、怎么跑通；学习笔记记录你自己学到了什么、哪里还没懂。

全文只有一条铁律：**同一句话只出现在一层，其他层用链接指过去。**

## 零、先判断：这条信息写在哪

| 你想写的内容 | 写到哪 | 例子 |
| --- | --- | --- |
| 这段代码为什么这样写、换了会出什么事 | 代码注释 | “必须用条件更新，否则并发 AC 会计两次分” |
| 一个模块由哪些文件组成、请求怎么走、异常怎么处理 | docs/modules/ | judge.md 里的“提交到终态的调用链” |
| 我今天学到了什么、哪里还没懂、为什么选这个方案 | docs/learning/ | 06.3-dev-services.md |
| 需求、接口契约、表结构、状态机 | docs/project-design.md | users 表的字段与索引 |
| 会影响后续开发的决策 | docs/adr/ | “为什么不缓存角色和账号状态” |

口诀：问“为什么” → 注释；问“是什么、怎么走” → 模块文档；问“我懂了没” → 学习笔记。

## 一、代码注释

### 1.1 只写四类内容

1. **为什么这样写**：被否决的替代方案、踩过的坑。
2. **边界条件**：空值、0、超时、并发、重启。
3. **安全约束**：不能返回、不能记录、必须校验的东西。
4. **容易被误改的设计决策**：改了会静默出错，而不是报错。

### 1.2 绝对不写

- 函数名已经说清的行为，例如 `# 返回健康状态`。
- 逐行翻译代码，例如 `i += 1  # i 加一`。
- 与代码不一致的过时注释。过时注释比没有注释更坏，宁可删掉。
- 大段架构说明。那是模块文档的位置。

### 1.3 例子：本项目的真实场景

差：

```python
# 检查是否有在途提交
count = await count_inflight(problem_id)
if count:
    raise Conflict()
```

好：

```python
# 不能只查数量再修改：并发提交可能在这两步之间插入新的 QUEUED，
# 判定与写入必须在同一事务里，锁住问题行串行化。详见 ADR-015。
async with lock_problem(problem_id):
    ...
```

差：

```python
# 返回状态、耗时、内存
return JudgeResult(status, time_ms, mem_kb)
```

好：

```python
# 隐藏测试点只回状态/耗时/内存：stdout 可能带出测试数据本身，
# 回传等于泄露答案（ADR-014）。
return JudgeResult(status, time_ms, mem_kb)
```

### 1.4 Docstring 的最小规范

- **模块顶部**：一句话说清这个文件负责什么。
- **公开函数**：一行摘要；只有参数、返回值、异常的含义不显然时，才写 Args / Returns / Raises。
- **私有函数**（下划线开头）：可以不写 docstring，用行内注释解释为什么。
- **路由函数**：`summary` 和 `description` 是给 OpenAPI 看的接口文档，不要在里面写实现细节。

### 1.5 自检一问

删掉这条注释，以后会不会有人改错？会 → 留；不会 → 删。

## 二、模块文档 docs/modules/

### 2.1 什么时候写

**模块稳定之后写一次。** 接口能跑通、测试通过、不再天天改它的时候写。不边开发边反复改。

模块还在变的时候，先写学习笔记；稳定后再整理成模块文档。

### 2.2 文件名

`docs/modules/<模块名>.md`，英文小写，和代码模块名对应：`auth.md`、`problem.md`、`judge.md`、`leaderboard.md`。

### 2.3 固定六节模板（复制即用）

```markdown
# 模块名

## 1 职责
一句话：负责什么，不负责什么。

## 2 主要文件
| 文件 | 作用 |
| --- | --- |

## 3 调用链
一次请求或一次判题，从入口到结束经过哪些函数。用编号列表，不用画图。

## 4 核心原理与关键决策
为什么这样组织；引用了哪份 ADR（写相对链接）。

## 5 异常与边界
会怎么失败：超时、重复、越权、资源不足。各自返回什么、留下什么状态。

## 6 怎么测
可复制的命令 + 预期输出。跑一次就知道模块是否还健康。
```

### 2.4 篇幅与更新

- 一页以内，约 60 行。写不下说明这个模块该拆。
- **必须更新**：对外接口变了、表结构变了、异常行为变了、依赖变了。
- **可以不更新**：纯内部重构、变量改名。但要顺手点开链接，确认没有断。

## 三、学习笔记 docs/learning/

### 3.1 什么时候写

每完成一个小节就写，**当天写**。不懂的地方当场记；攒到周末就写不出来了。

### 3.2 固定模板（每节一页以内）

```markdown
# <小节名>（日期）

目标：一句话。
验收：1… 2… 3…

做了什么：按顺序写命令与文件，让别人能复现。

我理解了什么：用自己的话写，不许复制代码。写不出来说明还没懂。

哪里没懂 / 待补：具体到哪个概念、哪一行。

遇到的坑与解决：现象 → 原因 → 怎么解决 → 以后怎么避免。

为什么选当前方案：被否决的选项是什么，为什么不用。

AI 使用记录：AI 做了什么、我批准了什么、我还没看懂什么。
```

### 3.3 好笔记的判据

三个月后的你，能不能照着这份笔记重新做完这件事？不能，就不是好笔记。

### 3.4 不要写

- 大段命令输出。留结果与结论即可。
- 成段代码复制。写文件路径加一句话。
- 流水账，例如“今天很累，装好了 Docker”。

### 3.5 为什么“我理解了什么”是硬要求

项目要你在面试时讲清自己的代码。能讲的前提，是当时真的用自己的话写过一遍。抄来的句子背不下来。

## 四、三层的关系（防重复）

| 信息 | 只写在一处 | 其他层怎么办 |
| --- | --- | --- |
| 为什么这行代码这样写 | 代码注释 | 模块文档写一句“见某文件”，不复述 |
| 模块由什么组成 | docs/modules/ | 学习笔记不重复，只链接 |
| 踩坑过程与没懂的点 | docs/learning/ | 模块文档只留结论，不留过程 |
| 接口契约、表结构 | docs/project-design.md | 其他层引用，不复制 |

自检：同一句话如果在两个文件里都出现，删掉一处，改成链接。

## 五、一个功能切片的推荐顺序

1. **写学习笔记（约 10 分钟）**：刚做完，记忆最热，把“怎么做的 + 哪里没懂”写下来。
2. **回代码补 2–3 条“为什么”注释（约 5 分钟）**：只补会让你改错的那几处。
3. **模块稳定后写模块文档（约 20 分钟）**：按六节模板填。
4. **检查链接**：模块文档指向 ADR，学习笔记指向代码路径。

顺序别反过来。先写模块文档容易写成“代码说明书”，先写注释容易写成“逐行翻译”。

## 六、提交前自检（逐条打勾）

- [ ] 新增或修改的函数，有没有解释“为什么”的注释？有明显非显然决策才需要。
- [ ] 有没有注释已经和代码不一致？过时注释比没有更坏。
- [ ] 接口或行为变了，docs/modules/ 是否同步？
- [ ] 本节的 docs/learning/ 里有没有“我理解了什么”，且不是抄代码？
- [ ] 三层之间有没有互相复制的同一段话？

## 七、常见错误对照

| 错误 | 表现 | 改法 |
| --- | --- | --- |
| 注释当翻译 | 每行都有一句中文 | 只留“为什么”，其余删 |
| 注释过时 | 代码改了注释没改 | 改代码时同步改，或直接删 |
| 注释替代文档 | 文件头写了两百行说明 | 挪到 docs/modules/ |
| 模块文档写成流水账 | 按开发顺序写“先建表再写接口” | 按结构写：职责、文件、调用链 |
| 学习笔记抄代码 | 大段粘贴实现 | 写“我理解了什么”，代码用路径引用 |
| 笔记攒着写 | 一周后一次性补 | 当天写；写不出来的就是没懂 |
| 文档没有测试方式 | 别人不知道怎么验证 | 第六节必须有可复制命令 |
| 三层重复 | 同一段话出现三次 | 留一处，其余改链接 |
| 只记成功不记失败 | 看不到踩过的坑 | 坑是最值钱的部分 |
