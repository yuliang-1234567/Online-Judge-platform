# 06.3 开发依赖与 Makefile（2026-10-19）

目标：只用 Compose 启动 MySQL、Redis，给本地 API 提供可验证的开发依赖。

三条验收：端口固定为本机13306/16379且没有代理注入；实际数据库/缓存 ping 与登录查询成功；Makefile入口可用、真实配置与缓存不入库。

配置：MySQL 8.0 与 Redis 7 使用官方镜像、独立数据卷；只绑定本机回环地址，分别映射到容器3306/6379。MySQL使用utf8mb4，Redis启用密码、128MB maxmemory与noeviction。环境只传服务需要的变量，没有使用整个env_file注入。API仍在WSL本地运行，没有API容器或业务表/迁移。

本轮实际使用的镜像 digest（2026-10-19）：
- `mysql:8.0` → `mysql@sha256:7dcddc01f13bab2f15cde676d44d01f61fc9f99fe7785e86196dfc07d358ae2b`
- `redis:7` → `redis@sha256:4fa24486b8bcca8eec45ee0eb166edc674795e53a2b53d1a9ef263eecebaac85`

分别用 `docker image inspect mysql:8.0 --format '{{index .RepoDigests 0}}'` 和同格式的 `redis:7` 命令读取。这是本轮镜像快照，Compose 仍使用浮动 tag，后续启动时可能换版本。

本地 deploy/.env 使用独立随机凭据，权限0600且被Git忽略，内容未打印；deploy/.env.example只含空密钥及占位符，并同步替代宿主端口。`dev-up` 在配置文件不存在时先输出“缺少 deploy/.env：先 cp deploy/.env.example deploy/.env 再填凭据”，检查分支以 `exit 1` 退出，不调用 Compose；GNU Make 对 recipe 失败的进程退出码为2。文件存在但必填变量缺失时，仍由 Compose 校验。

Redis 密码写在 `--requirepass` 参数上，会出现在 `docker inspect` 中；生产部署要改成 `aclfile` 或配置文件。

Makefile提供install/run/test/lint/fmt以及dev-config/dev-up/dev-check/dev-ps/dev-down。dev-up等待healthcheck；dev-check实际执行mysqladmin ping、应用账号SELECT 1和redis-cli ping。dev-down保留数据卷，不使用删除卷的参数。

验证结果：
- Windows原数据库/缓存端口被占用，替代端口与API端口在启动前空闲；WSL侧同样复查。
- make dev-config通过；只有mysql/redis服务，绑定配置正确，没有proxy环境键。
- make dev-up成功；随后mysqladmin输出mysqld is alive，应用账号查询返回1，redis-cli返回PONG。
- 运行中容器inspect确认没有代理变量；宿主TCP连接成功，两个服务均healthy。
- 首次验收后曾观察到两个容器同时退出255，随后观察到daemon重启；退出255的原因未查明、未复现。给本项目服务增加 `restart: unless-stopped` 后重新验收通过，但这不证明它修复了该次退出原因。该策略只保证 daemon 回来后自动拉起未被手动停止的服务，不保证 WSL 会话被回收期间服务在线；开发时需保留会话。
- make lint通过；Ruff格式检查3个文件无需修改；make test为1 passed、无警告。这个pytest用例仍只覆盖存活接口，服务ping属于本轮实际命令验证，没有编造新增集成测试。

Make由用户单独批准root安装，版本4.3；没有改动既有网络配置。服务与数据卷当前保留供后续开发使用。配置和学习记录尚未提交，等待用户审阅diff。
