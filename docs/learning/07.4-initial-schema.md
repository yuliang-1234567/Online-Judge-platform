## 我理解了什么

整理出的要点是：声明对齐、SQL 生成、真实数据库执行属于三层证据；测试要把实际迁移声明接到独立基线。以下解释由 AI 起草，尚不能据此判定用户理解检查通过。

## 五个理解检查题与答案

1. 为什么列类型用 mysql 方言？答：显式保留 unsigned、TINYINT 显示宽度和 DATETIME 的毫秒精度；只核列名会漏掉这些语义。
2. updated_at 为什么不用 server_onupdate？答：它不生成这里需要的 ON UPDATE DDL；把 CURRENT_TIMESTAMP(3) 与 ON UPDATE 放在同一个 server_default 文本中。
3. 复合约束为什么要核列序？答：联合主键/唯一约束是有序列组；幂等唯一键是 (user_id, idempotency_key)，复合主键列不自增，不能把名字相同当成定义相同。
4. downgrade 为什么先删外键再删索引、最后逆序删表？答：MySQL 外键可能依赖索引，先删索引会被拒绝；删表会丢数据，结构回退不能替代备份恢复。
5. 离线语义测试与 --sql 各证明什么？答：Recorder 直接核对 Column/约束属性与独立基线；--sql 证明 SQL 可生成，两者都不能证明 MySQL 接受、执行成功或约束真实生效。

## 遇到的坑与解决

只检查 AST 名字/顺序、SQL 对象数量会让错类型和多余默认值漏过；补直接读取属性的语义测试，并用真实失败的两个反例确认比较已接通。
比较前统一类型小写及 INTEGER/int 别名、拆分默认值与 ON UPDATE、去默认值外层引号；字符集/排序规则实际继承留待实库，不伪造离线结论。

## 为什么选当前方案

保留 step1/2/3 分层便于逐段核对和反向回退；基线保持独立，不为迁移迁就预期。收缩声明为“离线验证通过”，避免把建表代码完成当作数据库已建。
