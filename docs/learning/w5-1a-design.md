## 做了什么与设计口径

- 完整顺序为 JSON 解析 → 鉴权 → key 格式 → 请求限流 → 必需字段/类型 → 短读查重放 → 父锁及二次查 key → 新提交业务校验 → 在途检查 → 原子写入；见[主本 §5.1](https://github.com/yuliang-1234567/Online-Judge-platform/blob/c13940f97bd98a6d7cb397893eb90fa7d9014e29/docs/project-design.md#L264)。
- JSON 语法错误、基础字段/类型、key 格式和代码字段校验为 422/VALIDATION_ERROR；其他通用请求体解析异常可能为 400/HTTP_ERROR；整包实际字节超限为 413/PAYLOAD_TOO_LARGE；请求限流与在途上限分别为两类 429。
- 重放只在通过前置护栏并识别后忽略请求体差异；查询限定 user_id，返回原 submission_id、202 与 Idempotent-Replayed: true；仍经过请求限流，但不消耗在途额度，也不被原 QUEUED/RUNNING 记录挡住。
- Session 边界：鉴权事务先结束，独立短读事务结束后以新 Session 开创建事务；可复用物理连接，不继承旧事务。创建事务首条业务数据读取必须是父锁，之后二次查 key。
- 父锁按 problem id 获取、不按 status 过滤，DRAFT/OFFLINE 仍有父行；REPEATABLE READ 下的快照说明以“此前无普通一致性读或预建快照”为前提，不等于已核实运行隔离级别。
- 仅精确匹配 uk_sub_user_idempotency 的 1062 才进入重放竞争处理，完整回滚后新事务回读；1213/1205、其他唯一键或约束错误按系统错误处理，不包装成重放。
- 业务拒绝补查仅限取得父锁后：先回滚，再用新事务只查一次；不循环、不等待未来提交、不重复限流。
- 保留“首次 key 未命中 + 题目不存在 + 另一请求随后同用户同 key 创建”的 422 窗口；无对应父行锁、无 INSERT、无 1062，不扩大补查。
- 新提交业务校验、在途检查、提交行、限制快照与 user_problem_stats.attempts + 1 同事务；接收阶段不增加 submissions.attempts。
- 成功重放不新增提交、不增加用户提交次数或 claim 次数、不覆盖原限制快照及原始 request_id；日志必须区分创建与重放，本次请求追踪与原提交追踪分开。
- 重放不主动入队、不刷新 queued_at 或增加 enqueue_count；已持久化未入队交补偿扫描，可能等待 stale 阈值。120 s 是初始建议，不是固定恢复上界；恢复上界留给 W5-3。
- key 目标列级规则为 utf8mb4_0900_bin，原样保存、不做大小写/Unicode 归一化；MVP 无幂等 TTL、不自动清理，随提交保留，不承诺永久。新迁移与 schema guard 演进另开小节。
