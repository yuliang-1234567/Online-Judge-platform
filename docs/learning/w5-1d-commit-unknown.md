## 已批设计摘要与取舍

- W5-1d 采用候选 A：COMMIT 传输故障、应答丢失或本地等待超时导致结果无法确认时，本请求不另起确认查询、不重试写入、不主动入队；不扩大目标 1062 回读或父锁后一次 best-effort 补查。
- 满足旧资源退出、响应未开始及 HTTP 通道可用条件时，尝试 HTTP 503；统一 JSON 中 error.code=SUBMISSION_RESULT_UNKNOWN，并含 message 与本次 request_id；响应头为 X-Request-ID、Retry-After: 1，request_id 一致。不承诺具体送达时间。
- 该未知响应不返回 202、submission_id、status 或 Idempotent-Replayed；不写 submissions.error_code、不改 FAILED，也不把内部处理当作新的 HTTP 重放。
- 客户端至少等待 1 秒，以同用户、同 key、原请求内容最多自动重试一次；后续请求仍经过既有护栏，可能 429。再次未知则保留 key，不自动换 key 或无限重试；后续人工同 key 重试仍按正常协议处理。
- 数据库真实提交时，原事务的提交行、限制快照和用户提交次数增量保留；未提交则无这些写入，仍未结束时保持未知。COMMIT 确认后才由新建请求投递，已落库未投递交既有补偿，不改补偿阈值与计数。
- 5 秒是公开 commit() 调用的协作式取消预算，含内部回调、残余 flush、发送、等待应答与内部收尾；不含此前池等待、建连与业务 flush。须作用于实际执行 commit() 的任务，不能只取消被 shield 隔开的外层等待；不是驱动超时或请求硬上界。
- 2 秒仅为应用清理超预算告警阈值；依赖库在异常传到应用前的清理也须观测。不强行归还可疑连接，不承诺清理在 2 秒内完成，5+2 不是 7 秒响应承诺。
- 健康连接按可确认状态 rollback/close；可疑或失步连接先 invalidate 再本地退出，已 invalidated 只完成余下本地清理。唯一持有方负责退出，不盲发 ROLLBACK、不复用旧 Session、不用 engine.dispose() 或杀数据库连接代替请求清理；不证明远端已回滚或锁已释放。
- 外部 CancelledError 清理后继续传播，不转业务 503；逃到 Uvicorn 可能纯文本 500 或关连接。客户端断开、响应已开始或进程退出时不承诺 503，进程退出也不承诺应用清理完成。
- W5-1c 方案 B 不变：后续成功识别重放时，四入口各取识别查询所见状态，返回原 ID、202 和重放头，再用 GET 确认。不重开 W5-1a 四项决定或 W5-1b key 契约。
- 设计取舍：A 避免新增内部确认查询的等待与故障分支；代价是当前请求保留不确定性、不提供提交 ID，由同 key 后续请求及既有补偿衔接，不宣称已回滚。
