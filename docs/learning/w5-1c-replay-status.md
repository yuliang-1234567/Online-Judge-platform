## 做了什么与为何选择 B

- 仅替换设计第 270、298、312、1182、1194、1230 行；移除 body.status 待定表述，保留首次创建 QUEUED 示例，补齐客户端与状态表口径。
- B 返回识别重放的查询所见状态；与固定 QUEUED 相比，能表达原提交已经运行、完成或失败，代价是重放响应体可随读取时刻变化。
- 原 submission_id、202、Idempotent-Replayed: true 与既有无重复创建/计数/投递副作用约束保留，不新增 POST 响应字段。
- 同一次查询取得提交 ID 和 status，复制为响应标量；不在事务结束后依赖 ORM 隐式刷新，不为追求发送瞬间最新而追加锁或循环查询。
- 202 是原接受回执，不证明当前仍排队或判题成功；即使 POST 已携带终态，客户端也通过 GET 取结果、确认终态后停止轮询。
- QUEUED 不保证 broker 已收到任务；COMMIT 确认后投递失败不撤销创建成功，补偿耗尽仍可转 FAILED/ENQUEUE_EXHAUSTED，不改阈值、计数或恢复机制。

## 四个入口与场景判分（设计推演，未实跑）

| 入口 | 用于返回 status 的查询 |
| --- | --- |
| 独立短读命中 | 本次短读中识别 user_id/key 的查询 |
| 父锁后二次命中 | 取得父锁后的 key 查询，遵守 §11.6 首次一致性读前提 |
| 目标 1062 回读 | 完整回滚后，在新事务中识别同用户/key 的查询 |
| 父锁后业务拒绝补查 | 回滚后新事务唯一一次补查；不扩大原 best-effort 范围 |

- 每个入口均适用下表；成功重放都是原 ID、202、重放头 true，客户端 GET 确认，且不重复创建、计数或主动投递。
- QUEUED、RUNNING 及 §5.3 各终态均返回查询所见的原枚举值，不使用首次 QUEUED 常量；不同入口在不同时刻不必返回相同状态。

| 场景 | B 的预期与客户端行为 |
| --- | --- |
| 查询前已终态 | POST 202 携带对应终态，仍用 GET 取结果并确认 |
| 查询见 QUEUED，发送前改 RUNNING | POST 仍可为 QUEUED，GET 可随后见 RUNNING |
| 查询见 RUNNING，随后合法退回 QUEUED | POST 仍可为 RUNNING，GET 可随后见 QUEUED |
| 已持久化但未投递成功 | 可返回 QUEUED，不证明 broker 收到，不由重放触发补投 |
| 反复补偿无人领取后耗尽 | 查询见 FAILED 则返回 FAILED；内部原因为 ENQUEUE_EXHAUSTED，不向 POST 新增 error_code |

## 我理解了什么（用户本轮复述摘要）

- 四入口各取识别这次重放的查询所见值；这是查询快照，不保证响应发出时没变。
- 202 不代表仍 QUEUED 或判题成功；客户端 GET 到终态才停止，非终态按既有策略继续，GET 本身也不保证发送瞬间最新。
- QUEUED 是已落库、等待领取或再次领取；投递失败由补偿继续，耗尽可失败，既有机制不变。
- 本次设计复述通过；五项理解检查、关闭 AI 独立复现及实现运行证据不能由此替代，未完成部分仍待掌握。
