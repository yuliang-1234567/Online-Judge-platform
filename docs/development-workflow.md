## 1  项目定位与 MVP（新增）

原文所有流程都围绕「一个项目」展开，但没有写这个项目是什么。建议在写任何设计文档之前，先完成一页纸的项目简介（docs/00-project-brief.md）。

### 1.1  项目简介应包含

- 做什么、给谁用：一句话说清楚业务场景和目标用户。

- 核心业务流程：用户从开始到完成一件事，要经过哪几步。

- MVP 范围：第一版必须有的功能。

- 明确不做什么：写出来，防止范围蔓延。

- 成功标准：做到什么程度算可以演示、可以写进简历。

### 1.2  选题原则

- 尽量包含以下几点中的至少两点：权限控制、状态流转、事务一致性、并发或重复提交。纯增删改查的项目很难体现后端能力。

- 先看几份目标岗位的招聘要求，再反推技术栈，而不是先选技术再找场景。

- 规模以一个人能在计划工期内做完、做透为准。宁可功能少而深，也不要多而浅。

- 可参考的方向（仅举例，选题由你决定）：预约系统、订单与库存、任务或工单流转。

### 1.3  功能分级

| 级别 | 含义 | 示例 |
| --- | --- | --- |
| 必做 | 没有它项目不成立，必须完成并有测试 | 认证、核心业务流程、权限控制、基础测试、README 与一条命令启动 |
| 应做 | 体现工程质量，时间允许就做 | 幂等处理、事务一致性、日志、分页、CI |
| 可选 | 加分项，核心完成且验收通过后才考虑 | 缓存、异步任务、限流、监控 |

## 3  设计审查清单（补全第二部分）

原版第二部分写了「至少应该检查以下内容」，后面是空的。下面是可直接使用的清单，审查结论写入 docs/07-design-review.md。

| 类别 | 检查项 | 结论 / 修正 |
| --- | --- | --- |
| 需求一致性 | 每条需求都能对应到接口和数据表。<br>没有孤立功能，也没有没人用的接口。 |  |
| 数据库 | 唯一约束、外键、索引是否齐全。<br>时间字段、软删除策略是否统一。<br>选 3 到 5 个典型查询，检查能否用到索引、是否高效。 |  |
| API | 命名和状态码是否规范。<br>错误响应格式是否统一。<br>列表接口是否有分页。<br>鉴权放在哪一层。<br>关键写接口是否幂等。 |  |
| 安全 | 密码是否哈希存储。<br>权限边界：谁能改谁的数据。<br>输入校验放在哪里。<br>密钥等敏感信息如何管理。 |  |
| 事务与并发 | 哪些操作必须放在同一个事务里。<br>哪里可能出现重复提交、超卖或数据覆盖。 |  |
| 可测试与可部署 | 每个核心流程能否自动化测试。<br>配置能否区分开发、测试、生产环境。 |  |
| 范围风险 | 有没有超出 MVP 的设计。<br>每个模块的工期估计是否现实。 |  |

### 审查流程

- 自己先对照清单审一遍，把问题写下来。

- 让 AI 从不同角度再审（业务逻辑、安全、测试覆盖、可维护性），注意把它的意见当参考，不当结论。

- 每个问题记录：问题是什么、影响什么、怎么处理、当前状态。

- 修正设计文档，必要时重新审查被改动的部分。

- 确认第一阶段的实现范围（由垂直切片确定），再进入功能开发。

## 4  开发规范与环境

### 4.1  仓库初始化顺序

顺序很重要：敏感文件一旦进入提交历史，很难彻底清除。

- 创建仓库，先写 .gitignore 和 .env.example，确认 .env 已被忽略。

- 设置 git config core.quotepath false，避免中文文件名显示成转义乱码。

- 写 README 骨架：项目用途、技术栈、环境要求、基本运行方法。

- 建立项目目录、依赖配置和测试目录，确认测试能运行。

- 做初始提交。

- 配置 pre-commit 和 GitHub Actions，让每次提交或推送都自动执行检查。

### 4.2  建议的工具

| 用途 | 建议 | 说明 |
| --- | --- | --- |
| Python 版本 | 3.12 或更新的稳定版 | 选定后在 pyproject.toml 中固定 |
| 依赖管理 | uv（或 Poetry）+ pyproject.toml | 锁定依赖版本，保证可复现 |
| 代码检查与格式化 | Ruff | 一个工具同时负责 lint 和格式化 |
| 提交前检查 | pre-commit | 提交前自动跑 Ruff |
| 测试 | pytest、pytest-cov、httpx 或 TestClient | 覆盖率只作参考，见第 7 节 |
| 本地依赖服务 | Docker Compose | 一条命令启动数据库、Redis 等 |
| 数据库迁移 | Alembic | 迁移文件纳入版本管理，并验证回滚 |
| 配置管理 | pydantic-settings | 从环境变量读取，不写进源码 |
| 命令入口 | Makefile 或 justfile | 统一 install、run、test、lint、fmt |
| 持续集成 | GitHub Actions | 推送时自动跑 Ruff 和 pytest |

数据库具体选哪一种，以 docs/02-tech-stack.md 的选型结论为准。

### 4.3 OJ目录约定

OJ工程位于WSL2 Linux文件系统，示例为~/projects/oj-platform；不在/mnt/d下开发。Windows D盘只保留文档备份。
工程结构以 [设计第16章](project-design.md) 为准，避免维护第二份工程树。三份Word位于私有local-reference/且不入库；求职规划的内容不转成公开Markdown。

## 5  AI + 手动开发模式

### 5.1  每个小节的八个步骤

最重要的不是 AI 有没有生成代码，而是你能不能解释代码为什么这样写，以及它是否经过验证。

- 明确目标：用一句话写出本小节要做什么，再列 3 条验收标准。

- 理解设计与思路：先让 AI 讲解，然后用自己的话复述一遍。

- AI 给出实现建议：让它对比几种方案和取舍，不要直接要整份代码。

- 动手实现：核心逻辑自己写，样板代码可以让 AI 写；AI 写的部分由你审查。

- 读懂关键实现：关键函数、类和数据流都要能讲清楚。

- 运行测试验证：优先对照第 1 步的验收标准设计测试。

- 写学习记录：一页以内，同时记录 AI 使用情况（见 5.4）。

- Git 提交：测试通过后精准提交；如果是重大修改，按第 8 节的流程询问是否推送。

### 5.2  AI 的三种角色

| 角色 | 负责 | 使用时机 |
| --- | --- | --- |
| 技术导师 | 解释原理、架构设计、实现思路、方案优缺点 | 第 2、3 步 |
| 开发助手 | 写初始代码、补测试、排查错误、改进代码、写技术文档 | 第 4、6 步 |
| 代码审查者 | 检查是否符合需求、有无逻辑漏洞和安全风险、是否遗漏异常处理、是否过度复杂、是否缺少测试 | 第 5 步之后，以及模块完成时 |

### 5.3  不让 AI 自写自审

不要让 AI 写完代码、自己检查一遍，你就认为问题都解决了。建议这样协作：

```text
你提出需求 → AI 分析方案 → 你理解并确认 → AI 协助编码
→ 你检查改动 → 运行自动化测试 → AI 辅助分析失败原因
→ 你确认问题已解决 → Git 提交
```

重要模块可以让 AI 从四个角度分别审查：业务逻辑、安全、测试覆盖、可维护性。多次 AI 审查仍然不能代替实际运行测试。

### 5.4  AI 使用记录（新增）

在每篇学习记录末尾增加三行，面试被追问时能快速回忆：

- 哪些部分由 AI 生成。

- 哪些部分我做了修改，为什么改。

- 哪些部分我还没有完全弄懂。

另外可以让 AI 出题考你，比重读它的讲解更能检验是否真正掌握。

### 5.5  固定协作规则（新增）

把协作约定写进 docs/ai-workflow.md（或仓库根目录的 AGENTS.md），每次开新对话都让 AI 先读。建议包含：

- 先讲解，再写代码；不直接丢整份代码。

- 等我确认方案后才开始编码。

- 重大修改验证通过后，按 Git skill 询问是否推送。

- 不得编造未实现的功能或数据。

## 6  如何判断真的理解了

### 6.1  五项检查

| 检查项 | 通过标准 |
| --- | --- |
| 原理理解 | 能够解释当前小节为什么这样设计 |
| 代码理解 | 能够解释关键函数、类和数据流 |
| 修改能力 | 能够完成一个简单的变更 |
| 调试能力 | 能够定位至少一种典型错误 |
| 验证能力 | 能够独立运行测试并解释结果 |

### 6.2  分级严格度（新增）

「每次都完全懂了才进入下一节」对核心模块是对的，但对配置类内容会拖慢进度。建议分级：

| 级别 | 适用 | 要求 |
| --- | --- | --- |
| 严格 | 认证、权限、事务、核心业务规则、数据库设计 | 五项检查全部通过，并做一次「关闭 AI 后复现」，不允许带着疑问继续 |
| 标准 | 普通业务接口、查询、数据校验 | 原理、代码、验证三项通过，其余可以记入待补清单 |
| 宽松 | 环境、配置、工具、脚手架 | 能解释并修改配置即可 |

### 6.3  关闭 AI 后复现

- 不查看 AI 之前生成的解释。

- 根据自己的理解重新描述实现思路。

- 独立修改一小段代码。

- 独立运行测试。

- 对照之前的实现，找出自己的理解偏差。

不需要每个小节都重写全部代码。配置类任务只要能解释和修改配置；核心业务功能可以尝试独立实现一个简化版本。

### 6.4  待补理解清单（新增）

- 位置：docs/learning/open-questions.md。

- 没有弄懂的点记在这里，标准和宽松级别的小节允许带着少量问题继续。

- 每周固定回头清理一次；超过两周还没清掉的，升级为必须处理。

- 回答不上来不必否定自己，把它记录下来，继续学习、验证和实践。

### 6.5  自测题模板：以「用户注册」为例

完成一个功能后，你应该能回答下面这些问题，而不只是说「我用 FastAPI 实现了用户注册」：

- 请求如何进入后端？

- 参数如何校验？

- 密码如何安全存储？

- 如何处理重复用户名？

- 数据如何写入数据库？

- 数据库操作失败时如何处理？

- 如何防止用户提交非法数据？

- 相关测试如何编写？

- 出现错误时应该查看哪些日志？

- 为什么这样设计，而不是采用其他方式？

## 7  测试驱动的开发习惯

### 7.1  开发流程

```text
明确功能需求 → 定义验收标准 → 设计测试场景 → 实现功能
→ 运行测试 → 分析失败原因 → 修复问题 → 再次测试 → 确认完成
```

不要求一开始就严格 TDD。可以先学会为功能写测试，再逐渐尝试先写测试、后写实现。

### 7.2  测试类型与具体做法

| 类型 | 用途 | 具体做法 |
| --- | --- | --- |
| 单元测试 | 验证独立函数或业务逻辑 | pytest，不依赖数据库和网络 |
| 接口测试 | 验证请求参数、响应和错误处理 | TestClient 或 httpx，覆盖正常、缺参、格式错误、未授权 |
| 集成测试 | 验证数据库与多个模块协作 | 纯API测试可用事务回滚fixture；涉及Worker、独立进程或并发时使用独立测试库并清表 |
| 权限测试 | 验证不同用户能否执行对应操作 | 用参数化列出「角色 × 操作 × 预期结果」的矩阵 |
| 回归测试 | 确保修复问题后原有功能正常 | 每修复一个 bug，就留下一个能复现它的测试 |

### 7.3  以「用户注册」为例的测试场景

- 正常注册。

- 必填参数缺失。

- 参数格式错误。

- 用户名重复。

- 密码不符合规则。

- 数据库写入失败（用模拟故障触发）。

- 补充：并发重复注册时，由数据库唯一约束兜底。

- 补充：数据库中不存在明文密码。

实际需要哪些测试，应根据项目业务规则决定。

### 7.4  质量要求（新增）

- 覆盖率：核心业务逻辑达到 80% 左右即可，不追求 100%，覆盖率只是参考。

- 变异自检：故意把代码改坏，看测试会不会失败。测试没有失败，说明这个测试没起作用。

- 专项测试：幂等性、重复提交、并发扣减这类问题要专门写测试，面试时很有说服力。

- 测试命名统一：test_场景_预期结果，失败时一眼能看出什么坏了。

## 8  Git 规范与 Git skill

### 8.1  提交标准

- 提交的标准是完成了一个有明确意义、可以验证的修改，而不是按代码量或时间机械提交。

- 小节很大时拆成多个更小的提交；只是很小的配置修改时，不必为了提交次数而人为拆分。

- 数据库迁移文件纳入版本管理，并验证迁移和回滚。

- .env、密码、令牌、API 密钥不能提交。

### 8.2  提交流程

```text
git status                  # 看改了哪些文件
git diff                    # 看具体改了什么
（运行 ruff 和 pytest，通过后继续）
git add <相关文件>          # 不使用 git add .
git diff --cached --stat    # 复核暂存内容
git commit -m "feat(auth): 新增用户注册接口"
```

### 8.3  提交信息规范

| 类型 | 用途 | 示例 |
| --- | --- | --- |
| feat | 新功能 | feat(auth): 新增用户注册接口 |
| fix | 修复问题 | fix(order): 修复重复提交导致重复下单 |
| test | 测试 | test(auth): 补充重复用户名场景 |
| docs | 文档、学习记录 | docs(learning): 补充数据库连接学习记录 |
| refactor | 重构，行为不变 | refactor(core): 抽取密码哈希函数 |
| chore / ci | 构建、依赖、配置、CI | ci: 增加 Ruff 与 pytest 检查 |

### 8.4  Git skill 的行为约定

这部分已落成独立的 skill 文件 git-push-workflow/SKILL.md，核心约定如下：

| 场景 | 行为 |
| --- | --- |
| 主动询问 | 出现重大修改，并且已经验证成功（测试和检查通过、功能确认可用）时，Claude 询问是否推送，并在询问里写明推送位置（远程地址和分支）。<br>重大修改指：完成一个小节或功能切片、修复有测试覆盖的 bug、数据库迁移、依赖或配置或 CI 的重要变化、设计文档定稿。<br>小改动不打扰，先累积。 |
| 确认推送位置 | 每一次推送之前，都要你确认推送位置（远程地址和分支），确认只对这一次有效，没有例外。<br>主动询问时，一句话同时确认「推不推」和「推到哪」；你口述推送时，我先报出位置，等你确认后再执行。<br>位置与上次不同时会特别指出。项目暂时没有远程仓库时，我会问你 GitHub 仓库地址，不会擅自创建公开仓库。 |
| 你确认后 | 直接执行精准暂存、提交、推送，不再追问别的事；只有检查失败才会停下来。 |
| 你口述推送 | 说「推送」「push」即可进入流程，不要求必须是重大修改，但仍要先确认位置。如果发现测试未跑或有失败，会先提醒一次。 |
| 你选择不推送 | 不推送，也不对同一批改动重复追问。 |
| 推送前检查 | 核对分支和远程、查看 diff、运行 Ruff 和 pytest、检查敏感文件。任何一步失败都先停下。 |
| 暂存方式 | 按文件名暂存，必要时用 git add -p；一次提交只含一个逻辑修改；不使用 git add .。 |
| 禁止事项 | 不使用 --force 和 --no-verify，不改写已推送的历史，遇到冲突交给你决定。 |

### 8.5  推送说明怎么写

规则：推送说明只描述「本次推送完成后，相较于上一次推送完成后的项目，做了哪些更改」。只写变化，不写没变的内容和背景介绍。

- 比较基线是上一次推送后的远程状态（origin 上的当前分支），以此确定本次变化范围。

- 按新增、修改、删除三类写，具体到模块、文件、接口或数据表；某一类没有内容就省略。

- 末尾写验证方式和结果。

- 首次推送没有基线，注明「首次推送」，只列主要内容。

模板与示例：

```text
feat(auth): 新增用户注册接口
```

```text
新增：
- app/api/auth.py：POST /auth/register，校验用户名与密码规则
- users 表唯一索引 username，迁移文件 migrations/0002_users.py
- tests/test_register.py：6 个场景
```

```text
修改：
- app/core/security.py：新增 bcrypt 密码哈希函数
```

```text
验证：
- pytest：24 passed
- ruff check：无告警
```

### 8.6  其他建议

- 分支：个人项目可以直接用 main，也可以每个功能切片开一个短分支，合并后删除。

- 里程碑打标签，例如 v0.1-mvp，方便回退到稳定版本。

- Git 能帮你回答：功能什么时候实现、为什么改这个文件、某次修改引入了什么问题、改之前是什么样、如何回退到稳定版本。

## 9  文档与注释体系

### 9.1  三层记录

| 层 | 位置 | 记录什么 | 控制篇幅 |
| --- | --- | --- | --- |
| 代码注释 | 源代码中 | 不明显的业务规则、复杂算法、特殊边界条件、重要安全约束、容易被误改的设计决策 | 解释「为什么」，不重复「做什么」 |
| 模块文档 | docs/modules/ | 模块职责、主要文件、调用关系、核心原理、异常处理、测试方式 | 模块稳定后写一次，不边开发边反复改 |
| 学习笔记 | docs/learning/ | 学到了什么、哪里不理解、遇到的问题与解决、为什么选当前方案、还没弄懂什么 | 每节一页以内 |

不要把所有解释都堆进源代码，否则项目会变得臃肿。

### 9.2 docs目录

以 [设计第16章](project-design.md) 为骨架：project-design.md、development-workflow.md、ai-workflow.md、adr/、figures/、learning/、modules/、evidence/、loadtest/、interview-qa.md。
ADR统一放adr/，沿用设计文档001—012的编号和含义，新决策从013起。figures/每张图只有一份Mermaid Markdown源；reference/中的PNG仅作为v1.1原图存档。
00—07设计文件是通用模板中的组织示例；OJ已经有统一设计主本，不再复制出八份并行设计。

### 9.3  约定

- 文件名统一用英文，文件内容用中文。

- ADR（架构决策记录）只记会影响后续开发的重要决策，例如为什么选这个数据库、为什么用这种认证方式、为什么这样组织模块。不需要一开始写很多。

- API 文档在设计阶段写 Markdown 表格，开发后用 FastAPI 自动生成的 OpenAPI 核对已批准设计；不一致先停下报告，由用户确认后同步。

## 10  面向求职：积累技术证据

### 10.1  功能记录模板

每个重要模块用统一格式记录，内容必须是真实发生并验证过的：

| 项目 | 内容 |
| --- | --- |
| 功能名称 | 例如：用户认证模块 |
| 业务问题 | 要解决什么问题 |
| 实现方案与使用技术 | 根据实际实现填写 |
| 关键设计 | 认证流程、权限边界、异常处理 |
| 测试方式 | 正常登录、错误凭证、无权限访问等 |
| 遇到的问题与解决方法 | 记录真实发生的问题，以及实际采用的排查和修复方法 |
| 最终结果 | 记录经过验证的结果 |
| 后续改进 | 尚未解决或可以优化的地方 |

### 10.2  问题记录：失败比成功更有价值

每遇到一个真实问题，按下面六点记录，并写测试防止再次出现：

- 问题是什么。

- 如何复现。

- 为什么发生。

- 如何定位原因。

- 最终采用什么方案。

- 写了什么测试来防止回归。

### 10.3  原则

- 不要为了让简历好看而提前编造尚未实现的功能、性能数据或技术难点。可以在开发前规划，但简历里只写真正实现并验证的内容。

- 性能数据用 locust 或 wrk 自己压测得到，保证真实、可复现，并记录测试环境。

- 做出一两个有深度的点，比堆技术栈更有说服力。从缓存一致性、事务、幂等、异步任务、限流中，选你能讲透的。

### 10.4  建议交付物

- README：一条命令能启动，写清楚用途、技术栈、环境要求和运行方法。

- 架构图、ER 图、接口文档。

- 在线 demo 或演示录屏，能演示核心业务流程。

- 10 个「为什么这样设计」的面试问答。

- 项目复盘文档，包含问题记录和技术决策。

## 11  项目验收标准

开发前先定义什么叫完成，避免两个极端：只做最简单的功能而不完整，或不断加新技术而永远结束不了。标准应与项目规模和求职目标匹配，不必追求企业级监控、集群部署或高并发。

| 类别 | 验收项（完成后在前面打勾） |
| --- | --- |
| 功能 | ☐ 核心业务流程能完整运行。<br>☐ 关键接口的正常和异常情况都有处理。<br>☐ 用户权限符合预期。<br>☐ 数据库中的数据关系正确。 |
| 质量 | ☐ 核心业务逻辑有自动化测试。<br>☐ 项目能在干净环境中按文档重新运行。<br>☐ 没有已知的严重安全问题。<br>☐ 重要配置和敏感信息没有被提交到公开仓库。 |
| 部署 | ☐ 项目能按文档部署。<br>☐ 数据库初始化和迁移过程明确。<br>☐ 关键错误能通过日志排查。<br>☐ 数据备份和恢复方案符合项目需求。 |
| 求职 | ☐ README 清楚说明用途和运行方式。<br>☐ 有系统架构图、数据库 ER 图、接口文档。<br>☐ 有必要的测试记录。<br>☐ 能演示核心业务流程。<br>☐ 能独立解释主要技术决策。 |

冻结规则（新增）：必做项达到验收标准后，停止增加新技术。新想法统一记入 backlog，等项目复盘后再决定做不做。

## 12  最终执行流程（含时间控制）

时间占比是各阶段的上限，按计划总工期折算。设计类阶段合计不超过 20%。时间上限不覆盖严格级模块的理解与正确性门槛；非核心已知风险记录到审查记录或backlog，进度不足优先削减范围。

| 阶段 | 任务 | 主要交付物 | 验证方式 | 时间上限 |
| --- | --- | --- | --- | --- |
| 00 | 选题与 MVP 定义 | 项目简介 | 范围是否清晰，能否一句话说明 | 2% |
| 01 | 需求分析 | 需求分析文档 | 需求是否完整、可验收 | 3% |
| 02 | 技术选型 | 技术选型文档 | 验证关键技术可行性 | 2% |
| 03 | 架构设计与业务流程 | 架构文档、架构图、流程图 | 检查模块依赖和状态流转 | 4% |
| 04 | 数据库设计 | 数据库文档、ER 图 | 检查关系、约束和典型查询 | 2% |
| 05 | API 设计 | 接口文档 | 检查接口定义的一致性 | 2% |
| 06 | 工程初始化 | 仓库、环境、依赖、CI、Docker | 干净环境能启动，CI 能通过 | 4% |
| 07 | 垂直切片验证 | 一条最小可运行链路 | 注册、登录、一个核心接口、写库、一个测试、CI 通过 | 6% |
| 08 | 设计审查与修正 | 设计审查记录，修正后的设计 | 按第 3 节清单逐项检查，确认第一阶段范围 | 5% |
| 09 | 功能切片迭代 | 业务代码、测试、模块文档、学习记录 | 每个切片都包含实现、异常、安全、测试，按必做、应做、可选推进 | 45% |
| 10 | 集成与专项测试 | 集成测试、幂等与并发测试 | 验证模块协作，运行回归 | 8% |
| 11 | 部署与文档 | 部署配置、部署指南、README | 在干净环境按文档完整部署 | 7% |
| 12 | 复盘与求职材料 | 项目复盘、简历要点、演示材料 | 按第 11 节完整验收，核实每条描述的真实性 | 10% |

### 说明

- 阶段 06 到 07 是原版里没有的：设计初稿完成后先搭好工程，再跑通一条最小链路，用真实运行结果检验设计，然后才进入正式审查。

- 原版把异常处理和安全放在阶段 09，修订后它们属于阶段 09 每个功能切片的一部分，不再单独后置。

- 部署配置从一开始就用 Docker Compose 保持可运行，阶段 11 只是整理和验证，不是第一次部署。
