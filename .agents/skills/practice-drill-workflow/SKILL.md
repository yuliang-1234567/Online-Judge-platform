# practice-drill-workflow

## 何时用

严格级/标准级的实现小节（如 07.x），且用户明确选择“AI 先完整实现、自己在练习包重写一遍”。
用户未选择时，沿用 AGENTS.md 的默认协作模式；不把触发本 skill 当作实现、刷新或推送授权。
不用于：纯文档/配置/脚手架、紧急修复、只读审查轮。

## 角色

- Codex：解释设计、起草完整实现、生成练习包、跑检查、诊断与审阅、按授权提交和推送；不代改用户填空。
- 用户：在私有练习包重写选定核心、修复失败、完成五项理解检查与关闭 AI 后独立复现。
- 每个小节只选择有学习价值的核心目标，不要求重写全部文件；已掌握且未变化的目标不重复挖空。

## 产物（local-reference/practice/<小节>/，gitignored，永不入库）

- 00-路线图.md、run_practice.py、manifest-<小节>.sha256。
- 每主题四件：00-讲解.md、01-填空.py、02-参考.py、03-自测.md。
- 02 是仓库源码在“验收态”的只读快照：去掉 9 行元数据头后与源码逐字节一致（cmp=0）；两次授权刷新之间只读。
- 元数据记录来源、源 SHA-256、行数、生成时间、HEAD 与工作区范围；未提交源码不能只用 HEAD 标识版本。
- 01 生成后只由用户填写；只有明确授权的增量刷新可重挖列明的变化目标，其他用户答案不动。
- 仓库保留完整实现，不剥离函数体；练习答案不回移、不替代源码、不入库。

## 刷新时机与方式

验收态 = 该小节一个功能切片/修复完成 + 仓库 pytest/ruff/format 全绿 + 变更已定稿。
- 只有验收态才刷新；半成品不刷新，02 保持上一版并标记“包落后于源码”；此时 cmp≠0 不用于判定练习对错。
- 注释等不改行为的变化不单独触发刷新，随下一次验收态一起处理；提交前仍须满足 B1。
- 第一次生成应在用户开始填空前完成；同一文件后续变化时，在原包上增量更新：
  1. 列出影响目标，将当前包归档到 local-reference/handoff/backups/<小节>-<版本>-<日期>/；目标目录已存在则停止，不覆盖。
  2. 02 用当前源码更新，版本递增，台账保留旧/新 SHA 与行数。
  3. 01 只重挖变化目标：新增目标插入 TODO；语义变化目标重挖并标“本阶段需重填”；未变目标保留用户已填内容。
  4. 签名、依赖或测试变化若影响旧答案，先报告影响；未经明确授权，不静默覆盖或通过换 SHA 绕过复核。
  5. 讲解/自测追加“本阶段变更”，保留历史事实；当前有效定位与说明同步更新，过时内容标明适用版本。
  6. 更新 manifest、路线图及接线守卫；验证参考字节、目标范围和未变答案保护，再运行适用契约。

## 流程

1. 解释设计与取舍 → AI 实现源码 → 仓库默认测试、Ruff 与格式检查全绿。
2. 生成四件套：先验参考完整全绿；初始填空仅跑明确列出的 TODO 节点，精确全红。
3. 用户填空 → Codex 只诊断测试名、断言位置、期望、实际与异常，不改用户答案。
4. 用户修复并运行完整节点；实际通过率与失败清单如实记录，不为求绿改测试。
5. 写记录：AI 起草范围、用户修改、练习完成度与失败项、未回移、未验证边界、CI 核验状态及学习验收状态。
6. 实现小节按 git-push-workflow 拆主本和记录两个提交、一次推送；练习未全绿不阻塞代码交付，但提交门必须满足。
7. 后续验收态改动同一文件 → 按“刷新时机与方式”增量刷新，不恢复剥离或回移步骤。

## 练习验证契约

- 用新进程把练习文件按正式模块名接入测试，核对模块 __file__ 与目标 co_filename，不能实际测到仓库实现。
- 参考使用固定完整节点，必须全绿；初始使用明确的目标节点，失败集合与收集集合相等、收集非零、异常来源与 TODO 精确对应。
- 初始全红不要求所有完整节点都红；等待/取消等不适合初始验收的节点列入完整集合，说明排除原因。
- 每个挖空目标须有节点覆盖；初始与完整集合分别记函数级节点和参数化展开项数。
- 用户填写后使用完整集合统计结果；初始预期红、参考全绿均不代替用户完成态。
- 接线错误、零收集、意外外连或非指定 TODO 异常不能冒充初始验收通过；离线替身不证明实库、真实 Lua 或完整并发行为。

## 提交门（不满足不提交）

- B1 提交时该小节各包参考与对应源码 cmp=0；不匹配时停止，只有用户明确批准当前小节的例外才可放行，并记录差异、原因与范围，不沿用到其他小节。
- B2 仓库 pytest、ruff check、ruff format --check 全绿；用户练习的失败不能与仓库回归混为一谈。
- B3 来源、AI 起草、用户修改、按包练习通过率与失败项、未回移、未验证边界、学习状态、CI 核验状态记录齐全；CI 取不到写“未核验”及原因，不编数。
- B4 无凭据；真实 .env 与 local-reference 未入库；测试假值与真实部署值区分清楚。
- B5 提交粒度、精准暂存与推送前位置确认遵守 git-push-workflow，不因练习流程自动获得 Git 写权限。

## 学习验收（不挡代码提交，掌握前必验）

代码提交、练习全绿、理解验收分别记录；仓库通过检查即可按提交门交付并继续开发。
- E1 记录按包“通过/总数”、失败项与诊断时间；未全绿如实保留，不声明练习完成。
- E2 五项检查沿用既有定义：原理理解、代码理解、修改能力、调试能力、验证能力；还须完成关闭 AI 后独立复现。
- 独立复现可在私有目录完成一个核心片段或简化版本，独立说明思路、修改并运行相应测试、对照理解偏差；不看 AI 先前解释，不依赖 AI 代写。
- 任一检查或独立复现未完成，标“待掌握”并列待补项；全部通过后才标“已掌握”或“严格级理解验收通过”。练习全绿不能自动代替理解验收。
- E3 失败按实际证据归类为“未完成／行为不符／读参考后未重写”等；无法核实的过程写“未核实”，不凭代码相似度推断。
- 不以代码提交或继续开发宣称设计规定的严格级、实库或里程碑验收已经通过；不把尚未掌握的内容写成已掌握的简历或面试能力。

## 提交哪一份

唯一方式：提交仓库完整源码（AI 起草、经仓库测试验证的版本），记录来源与用户修改。
练习答案不回移、不替代源码、不入库；用户希望提交独立重写的代码时，另立流程。

## 失败处理

- 用户练习未全绿：保留失败及 E1–E3 记录，可继续代码交付；不得改测试、代填答案或把学习标成通过。
- 同一目标连续两轮仍红，提出缩小练习范围或改为读参考的建议，由用户选择，并记录学习方式变化。
- 除 B1 规定的用户明确例外外，任何提交门失败均停止提交并保留现场；不通过改守卫、删测试、覆盖答案或清空既有 diff 放行。

## 与仓库规则的关系

- AGENTS.md 定义协作模式及上层边界；本 skill 规定用户选定练习模式后的具体流程，不降低功能、安全、实库和里程碑验收标准。
- 提交/推送读 .agents/skills/git-push-workflow/SKILL.md；代码注释与文档读 .agents/skills/tech-doc-workflow/SKILL.md；每轮读 .agents/skills/risk-checkpoint/SKILL.md。
- 五项检查与独立复现的具体含义见 docs/development-workflow.md §6.1、§6.3；本项目的提交与学习验收时机以 AGENTS.md 为准。
- 启用本流程后，07.5a 旧剥离、回移安排终止；历史材料保留，不重写过去的验收记录，也不按旧路线图执行剥离或回移。
