# Git 推送工作流

目标：操作方便、提交精准、每次推送改了什么一眼能看清，并且不把敏感内容或未验证的改动推出去。

## 零、项目固定信息（换仓库或分支时只改这一节）

| 项 | 值 |
|---|---|
| 预期远程 | `origin → https://github.com/yuliang-1234567/Online-Judge-platform.git` |
| 仓库可见性 | **公开**（2026-10-19 由私有改为公开）。推送的内容任何人都能看到、克隆，删除后历史里仍可能留存 |
| 默认分支 | `main` |
| 检查命令 | Makefile 建立后以 Makefile 为准；此前用 README 已定义的入口；两者均未定义时用下述过渡口径 |
| 提交署名 | 不追加 `Co-Authored-By` 等署名行，用户要求时才加 |

"预期远程"只用来比对和提示，**不等于用户已经确认**。每次推送前仍然必须按第二节让用户确认。

过渡口径来自本项目 06.1—06.3 建立统一检查入口前，检查命令缺少来源的问题：在 Makefile 或 README 定义检查入口之前，从仓库根目录进入 `backend/` 执行：

```bash
cd backend
uv run ruff check .
uv run ruff format --check .
uv run pytest
```

以上仅为过渡口径。若当时 backend 或工具尚未就绪，如实记录未运行及原因，不把命令列出来当作已经通过。

## 一、什么时候触发

### 1. AI 主动询问

只有同时满足下面两个条件才询问：

- 本次修改是**重大修改**：完成了一个小节或功能切片；修复了有测试覆盖的 bug；新增或调整了数据库迁移；依赖、配置、CI、目录结构发生重要变化；设计文档定稿或修正。
- 修改已经**验证成功**：测试通过，ruff 检查通过，功能经过实际运行确认。纯文档修改的验证标准见第三节第 3 步。没有验证的修改不问。

小改动（改错别字、调整注释、局部重命名）不打扰用户，先累积，等攒成一次有意义的修改再问。

询问时用两三句话说清楚：做了什么变化、怎么验证的，并把推送位置写进去，最后问一句"是否推送到这里？"。不要附带长篇解释。

### 2. 用户口述

用户说"推送""push""提交并推送"之类的话，进入流程，不要求必须是重大修改，但仍然要先确认推送位置（见第二节）。如果检查发现测试没跑或有失败，提醒一次并说明原因，用户确认后才继续。

### 3. 用户拒绝

用户说不推送，就不推送，也不对同一批改动重复追问。之后的新改动累积到下一个合适的节点再问。

用户确认推送位置后，直接执行提交和推送，不再追问别的事；只有检查失败时才停下。

### 4. 小节级粒度（本项目硬规则）

- “小节”指项目里带编号的最小交付单元（如 06.1、07.1、07.2、07.3），或本文第一节所说的“功能切片”：单一目标、可独立验证、验收标准能三条说完。
- 判定标准：一个小节只承载一个独立逻辑变更，能用一句话说清“做了什么 + 怎么验证”。一旦需要“另外/顺便”补第二件事，就是跨了小节，拆成两个小节分别提交、分别推送；不要靠多加提交来容纳第二件事。
- 一个提交 = 一个逻辑单元。同一小节内按下面「主本与记录分开提交」拆成至多两个提交：主本类一个、记录类一个。
- 一次推送 = 一个小节。不把两个及以上小节的改动攒进同一次推送；该小节验收通过就推，不等别的小节。用户没说“等等再推”，就按小节推。
- 配套记录（README 里的数字、open-questions 的状态、学习笔记、evidence）属于该小节的记录提交，与主本提交在同一次推送内完成，不单独立项，也不跨小节积压。
- 同一小节的返工：未推送时并入同一提交；已推送则作为该小节的追加提交，不与别的小节混推。
- **主本与记录分开提交**：同一小节里同时改了主本类文件和记录类文件时，拆成两个提交。
  - 主本类：docs/project-design.md、docs/figures/、迁移文件、backend/ 的可执行实现、deploy/ 的配置与模板。记录类：README.md 的进度与数字、docs/learning/、docs/evidence/、docs/CHANGELOG.md。
  - 主本内部必须同步的改动不拆：设计与 ER 图、OpenAPI 与接口实现、迁移与模型，拆开会让仓库自相矛盾，放同一个提交。
  - 记录提交只写事实状态（进度、已落地、验证数字），不放主本内容。
  - 顺序固定：先主本提交，后记录提交。两个提交必须同一轮内完成并一次推送；不允许只推主本、把记录留到下次。
  - 一个小节最多两个提交；拆完还需要三个以上，说明小节本身太大，先拆小节再提交。

## 二、每次推送前确认推送位置

这条规则没有例外：**每一次推送之前，都必须让用户确认推送位置**，哪怕上一次刚确认过同一个位置。推送标签（`git push origin <tag>`）同样适用。

- 推送位置包括远程地址和分支。用 `git remote get-url origin` 和 `git branch --show-current` 获取，不凭记忆写，也不直接照抄第零节。
- 用一行写清楚，并标注可见性：`origin → https://github.com/yuliang-1234567/Online-Judge-platform.git，分支 main（公开仓库）`。可见性以第零节为准，不确定时问用户，不要猜。
- 主动询问时，把推送位置直接写进询问里，用户一次回答同时确认"推不推"和"推到哪"。用户口述推送时，先报出推送位置，等用户确认后再继续。
- 确认只对这一次推送有效，不沿用到下一次。
- 用户转述的指令里如果已经含有 `git push` 命令，不等于完成了位置确认：必须在本轮用 `git remote get-url origin` 与 `git branch --show-current` 读出实际位置并报出，等一句明确确认后再执行。
- 实际远程地址与第零节的预期远程不一致，或与上一次推送的位置不同，要明确写出"位置与预期/上次不同"，并列出两边的值。
- 用户指定了别的位置（另一个远程或分支）时，以用户说的为准，复述一遍请用户确认。
- 远程地址里带有令牌或密码时，展示时把凭据部分遮掉，并提醒用户改成不含凭据的地址。
- 本项目没有远程仓库、或 `origin` 不存在时，询问用户仓库地址；不要擅自创建仓库，更不要创建公开仓库。
- 开始提交之前，再核对一次当前远程和分支是否与用户确认的一致，不一致就停下来重新确认。

## 三、推送前检查

按顺序执行，任何一步失败都先停下来告诉用户，不要带着问题推送。

1. **位置与状态**：`git status`、`git branch --show-current`、`git remote -v`，确认与用户已确认的推送位置一致。再 `git fetch origin`，查看远程分支是否存在、是否有本地没有的提交。
2. **看改动**：`git diff --stat` 和 `git diff`，逐个确认本次改了哪些文件、改了什么。有未跟踪的新文件也要逐个过目。
3. **运行检查**：按第零节的检查命令运行，并如实记录结果。
   - 有代码改动：必须跑 ruff 和 pytest；失败就停。
   - 纯文档、纯配置改动且当前没有可运行的测试（例如仓库刚初始化）：不要写"测试通过"。在推送说明的验证部分写"未运行测试：<原因>"，并写明实际做过的检查（例如链接是否有效、暂存区无敏感文件）。
   - 不得编造检查结果；某条命令没跑就说没跑。
4. **敏感内容检查**：仓库是公开的，推送出去就等于公开，宁可多问一次。先看暂存区文件名，再在暂存 diff 里搜索可疑内容。发现任何一项就停止，告诉用户，并检查 `.gitignore`。
   - 绝不入库的文件：`.env`、`.env.*`（`.env.example` 除外）、`*.pem`、`*.key`、`id_rsa*`、令牌和凭据文件。
   - 数据与产物：数据库文件和备份（`*.sqlite`、`*.db`、`dump*.sql`、`*.sql.gz`、`backups/`）、判题运行产物（`judge-work/`、容器日志）、日志文件。
   - 真实题库的隐藏测试用例：设计要求保护测试数据，不入库；测试用的样例集 fixtures 可以入库。
   - 个人与部署信息：求职规划、简历原件、成绩单、含手机号邮箱住址或证件信息的文件；云服务器 IP、SSH 配置、云账号和域名后台信息。除非用户明确说要公开，否则不入库。
   - 环境垃圾：`__pycache__`、`.venv`、`node_modules`、`.idea/`、`.vscode/` 等个人配置。
   - 暂存 diff 里的可疑特征：`password=`、`SECRET`、`TOKEN`、`PRIVATE KEY`、`ghp_`、`github_pat_`、`AKIA` 等。
   - 单个文件超过 5 MB：提醒用户，确认后才继续。
5. 如果该小节有学习记录（`docs/learning/`），确认已经写好并放进同一次提交。缺失只提醒，不阻止推送。

## 四、精准暂存

- 不使用 `git add .`、`git add -A`、`git add -u`。
- 按文件名暂存：`git add <path>`；同一个文件里混了不相关的修改时，用 `git add -p` 只暂存相关部分。
- 一次提交只包含一个逻辑修改。发现修改里混了两件互不依赖的事，先回到第四节判断是不是跨了小节：跨了就拆小节；同一小节内的主本提交与记录提交不算“混事”，按第四节执行。
- 暂存后执行 `git diff --cached --stat`，确认暂存内容与预期一致，再提交。

### 未推送历史的拆分 / 重组

本项目曾把“纯转写基线”和“v1.2 修订”混在同一个本地提交里，随后在未推送时拆成两个提交；这类操作按以下流程处理：

1. 先确认涉及的提交从未推送，记录拆分前末端提交的完整 SHA（`<旧>`）和拟拆分范围；不能确认未推送就停下报告。
2. 按用户确认的基线与修订边界拆分 / 重组，只按明确路径暂存，各提交只包含对应修改。
3. 记录重组后末端提交的完整 SHA（`<新>`），必须证明最终文件树完全一致：`git rev-parse <旧>^{tree}` 与 `git rev-parse <新>^{tree}` 输出相等，或 `git diff <旧> <新> --exit-code` 返回 0。贴出实际输出及退出码，验证不一致就停下报告，不推送。
4. 终态文件树一致只证明没有丢内容，不证明拆分边界正确。还要逐个核对每个新提交的实际文件清单（`git show --stat <提交>`）与事先确定的边界一致；不一致就重做，不推送。
5. 只允许对未推送历史这样处理；一旦推送过就禁止改写，只能往前增加提交，不通过 amend、rebase、reset 或 force 绕过。

## 五、提交信息和推送说明

### 格式

采用 Conventional Commits：`type(scope): 一句话概括`。

| type | 用途 |
|---|---|
| feat | 新功能 |
| fix | 修复问题 |
| test | 新增或修改测试 |
| docs | 文档、学习记录 |
| refactor | 重构，不改变行为 |
| chore | 构建、依赖、配置 |
| ci | CI 配置 |

### 核心规则：只写变化

推送说明要回答一个问题：**本次推送完成后，相较于上一次推送完成后的项目，做了哪些更改。**

- 比较基线是上一次推送后的远程状态，即 `origin/<当前分支>`。先 `git fetch`，再用 `git diff --stat origin/<分支>..HEAD` 和 `git log --oneline origin/<分支>..HEAD` 获取变化范围。
- 只描述发生了变化的内容，分成新增、修改、删除三类，具体到模块、文件、接口或数据表。没有变化的部分不写，背景介绍不写，"优化了若干问题"这类空话不写。
- 末尾写验证方式和结果，例如"pytest：18 passed"。没有运行的检查如实写"未运行"，不要省略，也不要写成通过。
- 某一类没有内容就省略这一类。
- **首次推送**（远程分支还不存在或没有任何提交）：没有基线，在说明里写"首次推送"，只列仓库里包含的主要内容。
- 如果 `git fetch` 发现远程有新的提交（别的设备，或在 GitHub 网页上创建的 README、LICENSE 等），基线已经变了：先告诉用户远程多了什么，再按第七节处理，不要自己取舍。

### 模板：常规推送

```
feat(auth): 新增用户注册接口

新增：
- app/api/auth.py：POST /auth/register，校验用户名与密码规则
- users 表唯一索引 username，迁移文件 alembic/versions/0002_users.py
- tests/test_register.py：6 个场景（正常、缺参、格式错误、重复用户名、弱密码、写库失败）

修改：
- app/core/security.py：新增密码哈希函数

验证：
- pytest：24 passed
- ruff check：无告警
```

### 模板：首次推送

```
chore: 初始化项目仓库（首次推送）

新增：
- docs/：设计文档与开发准备方案
- AGENTS.md、.gitignore、.env.example、.gitattributes、README.md

验证：
- 未运行测试：尚无测试代码
- 已核对暂存区，无敏感文件
```

一次推送包含多个提交时，每条提交说明只描述自己那部分变化；推送完成后在回复里给用户一份汇总，同样只写相对上次推送的变化。用户希望留存时，再把汇总追加到 `docs/CHANGELOG.md`。

## 六、执行推送

1. **提交信息用文件传入**：把提交信息写进临时文件（UTF-8），用 `git commit -F <文件>` 提交，提交后删除临时文件。不要在命令行里用多个 `-m` 拼多行中文，Windows 的 PowerShell 和 cmd 在引号和编码上容易出错。
2. 不追加署名行，除非第零节或用户另有说明。
3. 推送到用户已确认的位置，明确写出远程名和分支，例如 `git push origin main`；该分支第一次推送用 `git push -u origin main`。
4. 打里程碑标签（如 `v0.1-mvp`）时：先确认标签名和位置，再 `git tag -a <名> -m "<说明>"` 和 `git push origin <名>`。
5. 推送完成后 `git status` 确认工作区干净，`git log -1 --stat` 确认提交内容。

### 禁止事项

- 不使用 `--force`、`--force-with-lease`，除非用户明确要求。
- 不使用 `--no-verify` 跳过钩子。
- 不改写已经推送的历史（包括对已推送提交做 amend、rebase、reset）。
- 不把令牌写进远程地址、命令或提交内容。

## 七、出问题时怎么办

出问题就停下，说清楚卡在哪一步、原因是什么、需要用户做什么。不要自己尝试绕过。

| 情况 | 处理 |
|---|---|
| 推送被拒绝（non-fast-forward） | 先 `git pull --rebase`，重新跑检查再推；出现冲突时交给用户决定，不自行取舍 |
| 远程已有本地没有的初始提交（常见于仓库在 GitHub 上带 README 创建），两边历史无关联 | 不 force，不自动合并。告诉用户远程有哪些提交，给出选项（先 rebase 到远程、或保留远程内容后合并），由用户选 |
| 认证失败（即使仓库公开，推送也需要登录；401/403/找不到仓库） | 提示用户用 Git Credential Manager 或 `gh auth login` 完成登录，必要时核对仓库名和账号权限；不要求用户把令牌发过来，不写进地址 |
| 钩子（pre-commit）失败 | 按提示修复后重新暂存、重新提交；不用 `--no-verify` |
| 沙箱、网络或审批限制导致命令无法执行 | 如实说明，并把需要用户在自己终端执行的命令完整列出来 |
| 发现密钥、令牌、密码或个人信息已经推送到公开仓库 | 立即告诉用户：按已泄露处理，先到对应服务商处作废并更换密钥。清理历史需要改写已推送的历史，只有用户明确要求才做，AI 不自行操作 |
| 检查发现敏感文件已被暂存 | 立即取消暂存（`git restore --staged <path>`），确认 `.gitignore`，如已进入提交历史且未推送，告诉用户并等待指示 |

## 八、回复用户的格式

推送成功后，回复保持简短：

```
已推送到 <仓库地址> 的 <分支> 分支（提交 <短哈希>）。
本次变化：
- 新增：……
- 修改：……
验证：……
```

推送失败时，按第七节的格式说明。

## 九、仓库初始化提醒（第一次提交之前）

- `.gitignore` 和 `.env.example` 已经建好，`.env` 已被忽略。本项目的 `local-reference/` 最终写入仓库级 `.gitignore`：会公开“本项目有私有材料”这一事实，但规则随仓库分发，换机 clone 后仍生效；`.git/info/exclude` 不公开、仅在本机生效，不随 clone 迁移，换机失效。这次选择前者，保留其公开可见性与可迁移性的取舍。
- 设置 `git config core.quotepath false`，中文文件名不会显示成转义乱码。
- 添加 `.gitattributes`，至少包含 `* text=auto eol=lf`。Windows 默认的 CRLF 换行会让 `.sh` 脚本和 Docker 入口脚本在 Linux 容器里报错。
- README 骨架已存在。
- 远程仓库是公开的，GitHub 上可能已经有初始提交，首次推送前先 `git fetch`，按第七节处理。
