# 三层记录工作流

目标：让初学者找到代码入口、理解关键机制与设计原因、识别异常和安全边界。代码附近说明阅读所需的局部信息；模块文档解释整体协作；学习笔记记录实际学习过程。

详细解释集中维护，其他层允许必要摘要与链接；阅读代码必须知道的前提留在代码附近，不能只让读者跳转。

## 零、适用范围与记录位置

### 0.1 范围与执行边界

- 代码注释与 `docs/` 下自维护的 Markdown（`.md`）文档同等重要，均须检查准确性、可读性及引用有效性；按各自职责组织内容，文档范围不限于模块文档和学习笔记。
- 按代码归属和职责判断：本项目全部自维护代码均适用，不使用目录、语言或前后端白名单。用户编写及 AI 生成后纳入项目维护的代码同样适用，未来新增目录和前端代码自动纳入。
- 业务实现、前端组件与交互、测试、迁移、工具、构建部署脚本及含执行逻辑的配置都在范围内；这些只是示例，不是封闭清单。
- 第三方依赖、缓存、锁文件、自动生成且不直接维护的产物，不要求手工补注释；自维护的生成模板仍适用。
- JSON 等不支持注释的文件不得插入非法注释；说明放在使用它的代码或已有对应文档。
- 所有相关代码变更都检查注释是否充分；简单直接或已有充分说明的代码可以不新增注释，不按条数或比例验收。
- 只读审核只报告缺口；触发本 skill 不代表获得修改权限。注释任务不顺手改变行为、接口、配置值或测试预期。

### 0.2 这条信息写在哪

| 你想写的内容 | 写到哪 | 例子 |
| --- | --- | --- |
| 局部入口、关键机制、设计原因与失败边界 | 代码注释 | Recorder 如何截获迁移声明，哪些结果仍需实库验证 |
| 一个模块由哪些文件组成、请求怎么走、异常怎么处理 | docs/modules/ | judge.md 里的“提交到终态的调用链” |
| 我今天学到了什么、哪里还没懂、为什么选这个方案 | docs/learning/ | 06.3-dev-services.md |
| 需求、接口契约、表结构、状态机 | docs/project-design.md | users 表的字段与索引 |
| 会影响后续开发的决策 | docs/adr/ | “为什么不缓存角色和账号状态” |

代码说明帮助读懂当前逻辑，模块文档串起跨文件协作，学习笔记记录本人理解；必要摘要可以重现，详细解释保持单一来源。

## 一、代码注释

### 1.1 按职责解释四个层次

| 层次 | 应说明的内容 |
| --- | --- |
| 文件或模块入口 | 负责什么、从哪里进入、与哪些组件协作；简单文件不强制套模板 |
| 核心函数或组件 | 不明显的输入输出、前提、副作用、异常和资源责任 |
| 关键逻辑段 | 怎样起作用、数据怎样变化、为何这样组织、改错会怎样 |
| 测试与替身 | 防什么错误、如何构造场景、替换了什么、断言能证明什么及不能证明什么 |

核心逻辑按职责识别：业务规则、权限、安全、状态转换、事务与并发、关键数据转换、外部调用、资源清理及测试验证机制。私有函数与嵌套函数不因名称而豁免。

### 1.2 面向初学者的写法

- 新增解释性注释以中文为主，代码标识符、协议名和必要术语保留原文。
- 在关键机制首次出现处说明它在本项目中的作用，例如测试替身如何截获调用；前端事件如何触发异步请求、结果如何更新状态，以及错误和资源释放由谁处理。
- 不逐行翻译赋值、循环和返回，不粘贴通用语法教程，不重复函数名已经说清的行为。
- 简单直接的代码保持简洁；长篇架构与教程放到对应文档。
- 注释与代码同步维护，过时解释需纠正；不能为迁就注释而改变已确认的行为。

### 1.3 例子：Recorder 与 Docker 生命周期

Recorder 的说明应解释替换机制和证据边界，而不是重复“调用 upgrade”：

```python
# 把迁移模块的 op 替换为内存记录器；upgrade 仍构造真实 Column/约束，
# 但建表调用只登记到 MetaData，不连接数据库，不能证明 MySQL 执行成功。
monkeypatch.setattr(module, "op", recorder)
module.upgrade()
```

Docker 超时的说明应解释资源归属和终止证据，而不是只写“杀容器”：

```python
# wait 客户端超时不代表后台容器已死；显式杀容器后再次 wait，
# 后续 inspect 还要核对 exited 与真实退出码，不能把 137 改写成成功。
docker("kill", "--signal", "KILL", name)
exit_code = int(docker("wait", name))
```

### 1.4 Docstring 与接口文档

- 模块或核心函数按 1.1 的实际阅读需要选择普通注释或 docstring，简单文件不强制套模板；私有、嵌套函数同样检查解释是否充分。
- 公开函数的参数、返回值或异常含义不明显时，补充相应契约；不要把所有函数机械写成 Args / Returns / Raises 模板。
- 路由的 summary、description 及会进入 OpenAPI 的 docstring 保持对外契约，内部教学说明放在普通注释。
- 纯注释回填既有 Python 文件时优先增加普通 # 注释，保留原 docstring、可执行语句与字符串常量，避免改变 CLI 帮助或自动生成的接口说明。

### 1.5 可读性自检

对每个核心逻辑段，检查读者能否从代码及附近说明回答：

1. 谁调用它，处理什么输入？
2. 关键机制和数据变化是什么？
3. 为什么采用当前做法？
4. 哪些前提、失败情况或副作用必须注意？
5. 对于测试，断言证明了什么、哪些结论仍不能推出？

缺失与该段相关的信息才补充；不要求每段都重复五个答案，不用注释条数代替理解。

## 二、模块文档 docs/modules/

### 2.1 什么时候写

**模块稳定之后写一次。** 接口能跑通、测试通过、不再天天改它的时候写。不边开发边反复改。

模块还在变的时候，先写学习笔记；稳定后再整理成模块文档。

### 2.2 文件名

`docs/modules/<模块名>.md`，英文小写，和代码模块名对应：`auth.md`、`problem.md`、`judge.md`、`leaderboard.md`。

### 2.3 固定六节模板（复制即用）

```markdown
# 模块名

## 1 职责
一句话：负责什么，不负责什么。

## 2 主要文件
| 文件 | 作用 |
| --- | --- |

## 3 调用链
一次请求或一次判题，从入口到结束经过哪些函数。用编号列表，不用画图。

## 4 核心原理与关键决策
为什么这样组织；引用了哪份 ADR（写相对链接）。

## 5 异常与边界
会怎么失败：超时、重复、越权、资源不足。各自返回什么、留下什么状态。

## 6 怎么测
可复制的命令 + 预期输出。跑一次就知道模块是否还健康。
```

### 2.4 篇幅与更新

- 一页以内，约 60 行。写不下说明这个模块该拆。
- **必须更新**：对外接口变了、表结构变了、异常行为变了、依赖变了。
- **可以不更新**：纯内部重构、变量改名。但要顺手点开链接，确认没有断。

## 三、学习笔记 docs/learning/

### 3.1 什么时候写

每完成一个小节就写，**当天写**。不懂的地方当场记；攒到周末就写不出来了。

### 3.2 固定模板（每节一页以内）

```markdown
# <小节名>（日期）

目标：一句话。
验收：1… 2… 3…

做了什么：按顺序写命令与文件，让别人能复现。

我理解了什么：用自己的话写，不许复制代码。写不出来说明还没懂。

哪里没懂 / 待补：具体到哪个概念、哪一行。

遇到的坑与解决：现象 → 原因 → 怎么解决 → 以后怎么避免。

为什么选当前方案：被否决的选项是什么，为什么不用。

AI 使用记录：AI 做了什么、我批准了什么、我还没看懂什么。
```

### 3.3 好笔记的判据

三个月后的你，能不能照着这份笔记重新做完这件事？不能，就不是好笔记。

### 3.4 不要写

- 大段命令输出。留结果与结论即可。
- 成段代码复制。写文件路径加一句话。
- 流水账，例如“今天很累，装好了 Docker”。

### 3.5 为什么“我理解了什么”是硬要求

项目要你在面试时讲清自己的代码。能讲的前提，是当时真的用自己的话写过一遍。抄来的句子背不下来。

## 四、三层的关系（防重复）

| 信息 | 详细解释维护在哪里 | 其他层怎么办 |
| --- | --- | --- |
| 局部机制、前提与设计原因 | 代码注释 | 模块文档可摘要并链接，必要前提仍留在代码附近 |
| 模块组成与跨文件调用链 | docs/modules/ | 代码只留局部协作说明，学习笔记按需摘要与链接 |
| 踩坑过程与没懂的点 | docs/learning/ | 模块文档只留相关结论，不复制过程 |
| 接口契约、表结构 | docs/project-design.md | 其他层引用，避免维护第二份完整定义 |

自检：详细解释是否重复维护、可能漂移？必要摘要不必删，但要指明来源；不让链接替代代码现场必需的信息。

## 五、一个功能切片的推荐顺序

1. **理解设计**：先找到设计依据、入口与协作边界，明确需要解释的关键机制。
2. **实现时同步说明**：在相关代码附近解释机制、原因和边界；简单代码不凑数。
3. **验证一致性**：核对解释是否符合实际行为，运行适用检查，纯注释修改确认逻辑未变。
4. **更新必要记录**：沿用上面的模板写学习记录；模块稳定后补模块文档，已有模块的契约与边界变化时同步更新。
5. **检查引用**：链接应有效；精确行号引用因代码移动而受影响时核对定位，不机械改写历史题目或历史验收结论。

已有代码回填也按理解、解释、验证的顺序逐批进行；不以注释代替用户的独立理解检查，不替用户宣称“已经理解”。

## 六、提交前自检（逐条打勾）

- [ ] 按代码职责检查了本次范围，未漏掉私有函数、测试替身或执行配置；无需新增的有具体理由。
- [ ] 核心逻辑的入口、机制、原因与相关边界可从附近读懂；没有逐行翻译或为凑数量加注释。
- [ ] 注释、docstring 与代码一致；接口文档未混入内部教学说明。
- [ ] 测试说明区分合成数据、实际声明和离线 SQL 的证据，未把它们写成真实数据库验证。
- [ ] 接口或行为变了，docs/modules/ 是否按需同步？
- [ ] 本节需要的学习记录如实区分 AI 生成、用户修改及未理解部分，没有代写“用户已经理解”。
- [ ] 详细解释有单一来源，必要摘要与链接有效，历史记录未被机械重写。

## 七、常见错误对照

| 错误 | 表现 | 改法 |
| --- | --- | --- |
| 注释当翻译 | 每行都有一句中文 | 删语法复述，保留必要入口、机制、原因与边界 |
| 范围写死 | 只给已有几个后端目录补注释 | 按代码归属与职责判断，新增目录和前端自动纳入 |
| 注释过时 | 代码改了注释没改 | 改代码时同步核对，纠正失效解释 |
| 注释替代文档 | 文件头写了两百行说明 | 长篇说明挪到 docs/modules/，局部前提仍就近保留 |
| 模块文档写成流水账 | 按开发顺序写“先建表再写接口” | 按结构写：职责、文件、调用链 |
| 学习笔记抄代码 | 大段粘贴实现 | 写自己的理解，代码用路径引用 |
| 笔记攒着写 | 一周后一次性补 | 当天写；写不出来的就是没懂 |
| 文档没有测试方式 | 别人不知道怎么验证 | 第六节必须有可复制命令 |
| 三层重复维护 | 同一段详细解释出现三次 | 详细解释集中，其他层保留必要摘要与链接 |
| 只记成功不记失败 | 看不到踩过的坑 | 记录失败原因与未验证边界 |

- 三层记录的定义：`docs/development-workflow.md` 第 9.1 节。
- 功能记录与问题记录模板：同文件第 10.1、10.2 节。
- 决策记录：`docs/adr/`，新决策从 ADR-013 起。
