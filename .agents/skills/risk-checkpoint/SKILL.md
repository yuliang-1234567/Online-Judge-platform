# 每轮风险拍板点

目标：把"要不要改方向"的决定权留在用户手里，同时不让它退化成每次追问一堆无关紧要的事。审查发生在动手之前，不是事后补记。

## 一、先审用户要求是否合理

每轮动手前，先判断本轮用户的要求本身有没有问题。执行方手快，一个不合理的要求被执行得越快，错得越大。看到下面任一条，先提出，不要闷头做：

1. **与主本冲突**：与 `docs/project-design.md`、`AGENTS.md` 或已批准 ADR 冲突，例如实现设计里没有的行为、绕过暂存与推送规则。
2. **不可逆**：删数据、改写已推送历史、force push、覆盖未备份文件、把凭据写进仓库。
3. **越权或环境风险**：root 入口、sudoers、代理与 DNS、镜像源、系统配置——必须先报目的、完整命令、影响面、回滚方式。
4. **验收不成立**：要求没有可核对的判据（"优化一下""搞好"），或验收标准之间互相矛盾。
5. **超出阶段边界**：做了本阶段明确不做的事（例如阶段 06 做 API 容器化、M1 之前改测试点数据模型）。
6. **前提不成立**：依赖的方案还没定、引用的文件或行号不存在、前后两句要求互斥。

处理分三档：

- 明显有问题 → 停下，说清问题 + 给一个替代方案，等决定；
- 拿不准 → 按最保守解释只做最小一步，同时说明歧义在哪；
- 无问题 → 不啰嗦，直接做。

**边界（最重要）**：用户明确指令优先级最高。指出问题后用户仍坚持，就按用户说的执行，并在回复里留一行「已知风险」；只有落在第 2、3 项（不可逆、越权与环境）时，必须等用户二次确认，不能用「用户已经坚持」放行。已经讨论过、用户拍过板的事，不再每轮重提。

## 二、什么时候列

每一轮回复的最后，无需用户提醒。交付代码、改文档、只读复核、给方案、跑验证的轮次都适用。

## 三、列什么

只列同时满足三条的：

1. 需要用户决定，而不是执行方自己能定的；
2. 不定就会返工、走偏或不可逆（数据、设计、公开历史、已推送内容）；
3. 是"选择题"，不是"待办事项"。

每条三行以内：风险一句话 → 为什么现在必须定 → 选项（可以给建议，但不替用户决定）。

## 四、不列什么

- 本轮或之前已经拍板过的，不重复提问。
- 已在 docs/learning/open-questions.md 挂账、且不必马上定的，不在这里重列，最多给一行指针。
- 纯说明、执行细节、改了也不影响交付物含义的，不列。
- 自己下一步打算做的事，不列。
- 为了凑满 3 条而编造的，不列——凑数比不列更糟。

## 五、没有风险怎么写

写一行：本轮无待拍板风险。

不要省略这一行：省略会被读成"忘了"，而"没问题就不用提"的自由裁量最容易被用来偷懒。

## 六、与 open-questions 的分工

本轮列出但未被决定的风险，由执行方在下次相关工作时记入 docs/learning/open-questions.md。本 skill 只管每轮即时暴露，不规定记录格式。

## 七、位置与格式

固定在回复最后，标题 ## 需你拍板；没有风险时也保留该标题，并写一行说明。对用户要求的审查结论写在回复开头：无问题时不必单独成段；有问题时先给问题和替代方案，再给执行结果。
